# 10｜机器学习工程与 MLOps

## 1. 机器学习系统不只是模型

```text
数据采集 → 验证 → 特征/表示 → 训练 → 评估 → 注册
   ↑                                         ↓
反馈与标注 ← 监控 ← 在线/批量服务 ← 部署与灰度
```

生产事故更多来自数据、接口、依赖和流程，而非模型公式。

## 2. 可复现项目结构

```text
project/
├── configs/        # 数据、模型、训练配置
├── data/           # 原始/中间/处理后数据约定
├── src/            # 可复用代码
├── tests/          # 数据、特征、模型测试
├── scripts/        # 训练、评估、部署入口
├── artifacts/      # 模型、指标、图表（通常不进 Git）
├── README.md
└── requirements.lock / environment.yml
```

配置与代码分离，避免在脚本深处硬编码路径、随机种子和超参数。

## 3. 版本化对象

一个可复现实验至少绑定：

- 代码版本。
- 数据快照或可重建数据的查询与哈希。
- 依赖与运行环境。
- 配置和随机种子。
- 训练硬件与时长。
- 评估结果与模型文件。

只保存 `.pth` 或 `.pkl` 文件不够，因为你可能不知道它由什么数据和代码产生。

## 4. 数据验证

在训练与推理入口验证 schema：列名、类型、范围、类别集合、缺失率、唯一性和时间顺序。把数据质量当成自动化测试，而不是出错后人工排查。

训练—服务偏差常见来源：

- 训练和线上使用不同预处理实现。
- 时区、单位或默认值不同。
- 特征计算窗口不同。
- 线上缺字段或类别编码不同。

尽量复用同一变换代码或将预处理与模型一起打包。

## 5. 离线、批量与在线推理

- 离线：一次性分析，延迟不敏感。
- 批量：定时为大量对象预测，架构简单、成本低。
- 在线：请求到达时实时预测，需考虑 P95/P99 延迟、吞吐、降级和缓存。
- 流式：事件持续到达并更新特征或预测。

选择最简单、能满足业务时效的方案。不是所有系统都需要实时服务。

## 6. 部署策略

- Shadow：新模型接收真实流量但不影响决策。
- Canary：少量流量逐步放大。
- A/B 测试：随机分流比较真实业务指标。
- Champion–challenger：稳定模型与候选模型并行对比。

必须有回滚路径。离线更优不保证在线更优，因为用户行为、系统反馈和延迟都会改变结果。

## 7. 监控什么

### 系统指标

延迟、吞吐、错误率、资源利用率、可用性。

### 数据指标

缺失率、范围、类别比例、特征分布、schema 变化。

### 模型指标

预测分布、置信度、校准、分群表现、真实标签到达后的效果。

### 业务指标

转化、成本、用户体验、安全事件等最终目标。

分布漂移是报警信号，不等于模型一定失效；性能下降也可能在边缘分布没明显变化时发生。

## 8. 反馈回路

模型输出会改变后续数据。例如推荐模型只曝光自己选择的内容，新数据因此带有策略偏差。风控模型拒绝申请后无法观察违约结果。需要探索流量、随机实验、反事实估计或因果方法处理。

## 9. 测试层次

- 单元测试：特征函数、损失、形状和边界值。
- 数据测试：schema、分布、重复、泄漏。
- 集成测试：训练到加载再到预测的完整链路。
- 回归测试：新版本不应无意改变固定样例结果。
- 性能测试：延迟、内存、吞吐。

## 10. 安全与隐私

考虑训练数据泄露、成员推断、模型反演、提示注入、供应链和对抗输入。采用最小权限、脱敏、审计、加密、保留期限和人工兜底。高风险系统不能只依赖模型自信度。

## 11. 技术债

模型代码常只是系统的一小部分。隐形依赖、无人负责的数据源、复制的特征逻辑、手工发布和缺少监控都会迅速积累。好的 MLOps 不是工具堆叠，而是让训练、评估、部署和回滚成为可重复、可审计流程。
